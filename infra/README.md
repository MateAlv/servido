# Infrastructure

Servido! runs on one AWS account on the **Free plan**, in `us-east-1`, defined with Terraform. Production runs three containers on one EC2 instance, with CloudFront in front for HTTPS: the same database and API images as `make up`, and a production web image (nginx with the React build) instead of the Vite dev server. Why it looks like this: [ADR 0008](../docs/decisions/0008-aws-free-plan-hosting.md). Diagrams: [docs/architecture/](../docs/architecture/).

```text
infra/
├── terraform/            Everything in AWS (apply from here)
│   ├── bootstrap/        One-time: the S3 bucket that stores Terraform state
│   └── user_data.sh.tftpl  First boot of the instance
└── ec2/                  What runs on the instance: compose.yml and deploy.sh
```

| Piece | Where | Size |
| --- | --- | --- |
| Public address (HTTPS) | CloudFront on `servido.discordia.fyi` (and its `*.cloudfront.net` address), certificate from ACM; the DNS is in Cloudflare | Price class 100 |
| Web: the React build, served by nginx, which forwards `/api` | Container `web` | — |
| API (FastAPI) | Container `api` | — |
| Database (PostgreSQL 17) | Container `db`, data on its own EBS volume | 8 GB gp3 |
| The instance running the three containers | EC2 + Elastic IP | `t4g.small` (2 vCPU, 2 GB), 12 GB gp3 |
| Backups | Data Lifecycle Manager: a snapshot of the database volume every night at 06:00 UTC (03:00 in Buenos Aires), last 7 kept | — |
| Secrets: `/servido-prod/postgres-password` and `/servido-prod/jwt-secret` (the key that signs login tokens) | SSM Parameter Store (SecureString), generated by Terraform; `deploy.sh` writes them to `infra/ec2/.env` on every deploy | Standard tier |
| Deploys | GitHub Actions → OIDC role (only for `main`) → SSM Run Command on the instance | — |
| Mail | Amazon SES, sending as `no-reply@servido.discordia.fyi` with Easy DKIM. The api container uses the instance role, so there are no keys. | — |
| Spend alert | AWS Budgets: email to `alert_emails` at 80% of actual spend and at 100% of forecast spend | USD 15/month |
| Memory headroom | A 1 GB swap file, created on first boot | — |

The containers are defined in [ec2/compose.yml](ec2/compose.yml). The web image is [frontend/Dockerfile](../frontend/Dockerfile) with [frontend/nginx.conf](../frontend/nginx.conf); the API image is the same [backend/Dockerfile](../backend/Dockerfile) that `make up` uses.

## Changes to `main`

`main` is protected by a GitHub ruleset: every change goes through a pull request with one approval from another team member and the checks `backend`, `frontend`, `infra` and `check` in green. Force-push and deleting the branch are blocked. Terraform changes are never applied by CI: whoever changes `infra/terraform/` runs `terraform plan` and `apply` by hand.

## Free plan rules

The account must stay on the Free plan: it never bills real money, and when the credits or the 6 months run out it closes. These rules keep it that way.

- **Only Free-plan-eligible sizes.** EC2: `t4g.small` (default), `t4g.micro`, `t3.small` or `t3.micro`; the variables reject anything else.
- **Never** join or create an AWS Organization, set up Control Tower or IAM Identity Center, buy Savings Plans or Reserved Instances, or subscribe to AWS Marketplace products. Joining an Organization or setting up Control Tower upgrades the account to the paid plan for good, and IAM Identity Center normally sits on top of an Organization.
- Plain IAM users, roles and the GitHub OIDC provider used here are fine.
- No RDS, NAT gateways, load balancers or extra environments: one instance runs everything.
- Every change goes through Terraform, never the console, so `terraform destroy` can clean everything at the end.

## First setup

Whoever creates the account:

1. Sign up at aws.amazon.com and choose the **Free plan**. Turn on MFA for the root user.
2. Create an IAM user for the person who runs Terraform, with `AdministratorAccess` and MFA. Do not use the root user day to day.

Whoever runs Terraform (needs Terraform ≥ 1.10, AWS CLI ≥ 2.32 (for `aws login`), `gh` and the Session Manager plugin):

```bash
# 1. Credentials for this account only, in their own profile
aws login --profile servido              # browser sign-in as the IAM user, no stored access keys
export AWS_PROFILE=servido AWS_REGION=us-east-1
aws sts get-caller-identity              # check it is the Servido! account

# 2. One-time: the bucket for Terraform state
cd infra/terraform/bootstrap
terraform init && terraform apply
terraform output -raw backend_config > ../backend.hcl

# 3. The environment
cd ..
cp terraform.tfvars.example terraform.tfvars   # set alert_emails
terraform init -backend-config=backend.hcl
terraform plan                                 # read it: only the pieces in the table above
terraform apply                                # a few minutes, CloudFront is the slowest

# 4. Wait about 10 minutes for the instance's first boot (it builds the images), then
curl "$(terraform output -raw api_health_url)" # {"status":"ok","database":"ok"}

# 5. Let GitHub Actions deploy (run from the repository root, needs repo admin)
terraform -chdir=infra/terraform output -raw github_variables | bash
gh workflow run deploy.yml
```

After that, every merge to `main` that touches `backend/`, `frontend/`, `infra/ec2/` or `.github/workflows/deploy.yml` deploys automatically: the instance pulls the commit and rebuilds the containers, and migrations run when the API starts. The app is at `terraform output site_url`.

## Custom domain

The app answers on `servido.discordia.fyi`, a subdomain of a domain Mateo owns, whose DNS is in Cloudflare (not in AWS). The certificate comes from ACM, is free and renews itself as long as its validation record stays in Cloudflare. To set it up, or to move to another domain with `domain_name`:

```bash
cd infra/terraform
# 1. Create the certificate on its own, then print the records to add
terraform apply -target=aws_acm_certificate.site
terraform output cloudflare_dns_records
```

2. In Cloudflare → the domain → DNS → Records, add both CNAMEs from the output with **Proxy status: DNS only** (grey cloud). Proxying them through Cloudflare breaks the certificate validation.
3. Run `terraform apply`. It waits until ACM validates the certificate (a few minutes) and then adds the domain to CloudFront (about 5 more minutes).
4. Check: `curl "$(terraform output -raw api_health_url)"`.

Without a domain, set `domain_name = null` in `terraform.tfvars`: the app keeps only the `*.cloudfront.net` address.

## Mail (Amazon SES)

The API mails the diner's verification link (spec 007, US-51, [ADR 0009](../docs/decisions/0009-google-sign-in-and-ses-mail.md)). In production `MAIL_BACKEND=ses` (`infra/ec2/compose.yml`), or `smtp` while the Gmail fallback below is on. Locally the link is printed in the API log instead.

One-time setup:

1. `terraform apply` creates the SES identity for the domain, lets the instance role send, and raises the instance metadata hop limit to 2 so the api container can use that role.
2. `terraform output ses_dkim_records` prints three CNAMEs. Add them in Cloudflare with **DNS only**. SES shows the domain as verified within minutes to hours.
3. SES starts in the **sandbox**: it only delivers to verified addresses. Request production access once: SES console → Account dashboard → Request production access (transactional mail, account verification, a few mails a day). Until AWS approves it, add the testers' addresses under SES → Identities.

### Gmail instead of SES

While SES has no production access, the API can send from **servido.gdsi@gmail.com** over SMTP (`MAIL_BACKEND=smtp`). `deploy.sh` switches to it whenever the SSM parameter `/servido-prod/smtp-password` exists:

1. In the team Google account, turn on 2-Step Verification and create an app password (myaccount.google.com/apppasswords).
2. Store it without pasting it anywhere else; the prompt keeps it out of the shell history:
   ```bash
   read -rs SMTP_PASSWORD && AWS_PROFILE=servido aws ssm put-parameter --region us-east-1 \
     --name /servido-prod/smtp-password --type SecureString --value "$SMTP_PASSWORD" && unset SMTP_PASSWORD
   ```
3. Redeploy (Actions → Deploy → Run workflow).

To go back to SES, delete the parameter (`aws ssm delete-parameter --name /servido-prod/smtp-password`), revoke the app password and redeploy.

If a mail can't be sent, registration still succeeds and the API logs `Could not send the verification mail`; the diner can press "Reenviar mail de verificación".

## Day to day

Commands marked *(shell)* run in a Session Manager shell on the instance.

| Task | Command |
| --- | --- |
| Shell on the instance | `aws ssm start-session --target "$(terraform output -raw instance_id)"` |
| State and logs *(shell)* | `cd /opt/servido/infra/ec2`, then `sudo docker compose ps` and `sudo docker compose logs -f api` |
| Deploy by hand | `gh workflow run deploy.yml`, or `sudo /opt/servido/infra/ec2/deploy.sh main` *(shell)* |
| Add or rotate a secret | Change `secrets.tf`, `terraform apply`, then deploy. Apply **before** merging code that needs a new secret: the deploy fails while the parameter is missing, and the running containers stay up |
| SQL console *(shell)* | `sudo docker compose -f /opt/servido/infra/ec2/compose.yml exec db psql -U servido` |
| Dump before a risky migration *(shell)* | `sudo docker compose -f /opt/servido/infra/ec2/compose.yml exec db pg_dump -U servido servido > ~/before-<name>.sql` |
| List the nightly snapshots | `aws ec2 describe-snapshots --owner-ids self --filters Name=tag:Snapshot,Values=servido-prod-daily --query 'Snapshots[].[StartTime,SnapshotId]' --output table` |

### Restoring a snapshot

This replaces the database with the state of that night, and replaces the instance too. Data written after the snapshot is lost.

```bash
cd infra/terraform
terraform apply -replace=aws_ebs_volume.data -var data_snapshot_id=snap-0123456789abcdef0
terraform output -raw github_variables | bash   # the instance ID changed
```

The new instance mounts the restored volume and deploys `main`, as on the first setup.

## When things fail

| Symptom | Fix |
| --- | --- |
| The budget alert fires in the first month | The `t4g.small` free trial is not applying to this account: check the EC2 line under Billing → Bills. Either accept about USD 17.6/month (still inside the credits) or set `instance_type = "t4g.micro"` (about USD 11.4/month in total, 1 GB of memory). |
| `FreeTierRestrictionError` or "not eligible for Free Tier" about the instance size | Use the defaults; the Free plan rejects anything bigger. |
| `InsufficientInstanceCapacity` | Try again later, or `instance_type = "t3.small"`. |
| `EntityAlreadyExists` for the GitHub OIDC provider | Someone created it already: `terraform import aws_iam_openid_connect_provider.github <arn>` |
| `terraform apply` waits on `aws_acm_certificate_validation` | The validation CNAME is missing or proxied in Cloudflare. Check it with `dig +short CNAME <name from the output>`. |
| Health check fails after apply | The first boot takes about 10 minutes. Then check `/var/log/cloud-init-output.log` and `sudo docker compose ps` *(shell)*. |
| Disk full on the instance | `sudo docker system prune` *(shell)*. The database is on its own volume and is not affected. |
| Deploy fails with `Not authorized to perform sts:AssumeRoleWithWebIdentity` | The repository's OIDC subject changed. Compare `gh api repos/MateAlv/servido/actions/oidc/customization/sub` with `github_oidc_subject_prefix` and apply. |
| Deploy fails with `JWT_SECRET` (or another variable) "required" | The SSM parameter does not exist yet: `terraform apply`, then `gh workflow run deploy.yml`. |
| The Deploy workflow cannot find the instance | The instance was replaced (for example by a change in `user_data.sh.tftpl`): run step 5 of the first setup again. |

## At the end of the course

```bash
terraform -chdir=infra/terraform destroy
terraform -chdir=infra/terraform/bootstrap destroy
```

Only whoever ran the bootstrap can destroy it: its state is local, like `backend.hcl` and `terraform.tfvars` (all gitignored). `destroy` leaves the nightly snapshots behind. Delete them with the IDs from "List the nightly snapshots" (`aws ec2 delete-snapshot --snapshot-id <id>`), or simply let the Free plan account close.
