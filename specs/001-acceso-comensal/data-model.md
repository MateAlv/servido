# Data model: Diner account access

## `comensales`

SQLAlchemy model: `Diner`

| Column | Type | Null | Constraints / behavior |
| --- | --- | --- | --- |
| `id_comensal` | UUID | no | Primary key, generated by the application/database |
| `nombre` | `VARCHAR(60)` | yes | Must contain non-whitespace text when present; required by the registration API |
| `email` | `VARCHAR(255)` | no | Unique; trimmed and lowercased before persistence; email-shape check |
| `password_hash` | `VARCHAR(255)` | no | Argon2 hash only; never returned or logged |
| `fecha_registro` | `TIMESTAMP WITH TIME ZONE` | no | UTC creation timestamp, server default |

`nombre` was added by the second migration after the team decided on 21/10 that
registration also asks for the diner's name. The column is nullable only for
accounts created before that change; `POST /api/comensales` requires it. The
blueprint's `apellido` and `telefono` are still excluded.

## `restaurantes`

SQLAlchemy model: `Restaurant`

| Column | Type | Null | Constraints / behavior |
| --- | --- | --- | --- |
| `id_restaurante` | UUID | no | Primary key |
| `nombre` | `VARCHAR(150)` | no | Must contain non-whitespace text |
| `cuit` | `CHAR(11)` | no | Unique; exactly 11 digits |
| `email` | `VARCHAR(255)` | no | Unique; email-shape check |
| `telefono` | `VARCHAR(30)` | no | Must contain non-whitespace text |
| `password_hash` | `VARCHAR(255)` | no | Argon2 hash; used by restaurant login (spec 003) |
| `direccion` | `VARCHAR(200)` | yes | Must contain non-whitespace text when present; filled in later (US-6, US-8) |
| `barrio` | `VARCHAR(60)` | yes | Must contain non-whitespace text when present; filled in later (US-6, US-8) |
| `tipo_comida` | `VARCHAR(60)` | yes | Must contain non-whitespace text when present; filled in later (US-6, US-8) |

This feature created the table; spec 003 (US-2, US-4) later added `telefono`,
made the profile columns nullable, and exposes restaurant registration
(`POST /api/restaurantes`) and login (`POST /api/auth/restaurante`). Those
endpoints are outside this feature's contract.

## Relationships

There are no foreign keys or relationships between these two tables in this
feature. Diner and restaurant emails are unique independently; the spec states
that the accounts are independent.

## Validation and invariants

- Email normalization occurs before both validation and lookup.
- Passwords are validated at the API boundary: 8–128 characters, at least one
  letter and one number, any other characters accepted, and password not equal
  to the normalized email.
- A database unique constraint prevents duplicate diner accounts even if the
  registration request is submitted twice.
- Database constraints retain the blueprint's email, CUIT, and nonblank-text
  protections.
- No session table is added. Authentication is stateless for this spec: after
  successful login, the server returns a JSON response containing a JWT signed
  with HS256, using an environment-provided secret and a one-hour expiration.
  Cookies are not used and sessions are not persisted in PostgreSQL.

## Migration strategy

The first Alembic revision (`001_add_account_tables`):

1. Creates `comensales` with the UUID primary key, unique normalized email,
   password hash, and timezone-aware creation timestamp (no `nombre` yet).
2. Creates `restaurantes` with the columns listed above except `telefono`,
   with `direccion`, `barrio`, and `tipo_comida` as `NOT NULL`.
3. Creates the named unique and check constraints using the metadata naming
   convention.
4. Drops `restaurantes` and then `comensales` in `downgrade()`.

The migration must be generated with the repository's Alembic configuration,
reviewed, and applied with `make migrate`. It must not create any table from
the remaining SQL blueprint.

## Restaurant-account migration (spec 003)

The second revision (`002_restaurant_names`, file
`backend/migrations/versions/002_restaurant_name.py`) evolves both tables with
`op.add_column()` and `op.alter_column()`, without recreating or renaming them:

1. Adds nullable `comensales.nombre` with a nonblank check.
2. Adds `restaurantes.telefono` as `NOT NULL` with a nonblank check. This is
   safe because no restaurant could register before this revision.
3. Makes `direccion`, `barrio`, and `tipo_comida` nullable and relaxes their
   nonblank checks to allow `NULL`, because registration does not ask for them.

No `auth_provider` column exists: Google sign-up moved to US-28 (Sprint 4).
