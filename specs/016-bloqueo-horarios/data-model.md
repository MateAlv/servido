# Data Model: Bloquear Horarios No Disponibles (US-32)

One new table owned by this feature: `closures`. The existing `reservations`, `turnos`,
`table_inventory`, `carts` and `pedidos` tables are read or updated through their existing rules.
No new column is added to any existing table.

## `closures` (Bloqueo)

Model: `backend/app/models/closure.py`. Created by one Alembic revision after
`merge_reviews_terms_20261107`.

| Column | Type | Null | Constraints / behavior |
| --- | --- | --- | --- |
| `id` | `UUID` | no | Primary key |
| `restaurant_id` | `UUID` | no | FK → `restaurantes.id_restaurante`, `ON DELETE RESTRICT` |
| `date` | `DATE` | no | Buenos Aires local date of the closure |
| `start_time` | `TIME` | yes | Local start of the range; `NULL` only for a whole-day closure |
| `end_time` | `TIME` | yes | Local end of the range; `NULL` only for a whole-day closure |
| `created_at` | `TIMESTAMPTZ` | no | Default `CURRENT_TIMESTAMP` |
| `request_id` | `UUID` | no | Generated by the page once per block attempt; **unique**; a repeated request returns the existing closure |

Constraints:

- `closure_times_complete`: `(start_time IS NULL AND end_time IS NULL) OR
  (start_time IS NOT NULL AND end_time IS NOT NULL)`.
- `end_after_start`: `start_time IS NULL OR end_time > start_time`.
- `uq_closures_request_id`: unique on `request_id` (double submit, S4/edge).
- `ix_closures_restaurant_id_date`: for the listing and the availability reads.
- No exclusion/unique constraint on `(restaurant_id, date, start_time, end_time)`: the spec allows
  overlapping closures, and a second identical closure is harmless.

All constraints are declared in the SQLAlchemy model (`__table_args__`), so `alembic check` in CI
sees no drift between the model and the migration.

## Relationship

```text
Restaurant 1 ── * Closure
Restaurant 1 ── * Reservation
Reservation 1 ── 0..1 Order
Reservation 1 ── 0..1 Cart
```

## Rules (single source: `backend/app/services/closures.py` and `services/availability.py`)

1. **Range shape**: both times `NULL` means the whole day (`[date 00:00, date+1 00:00)` in
   Buenos Aires); otherwise the range is `[date start_time, date end_time)`. `end_time` must be
   strictly later than `start_time`. Only one of the two times is a `400`.
2. **Past dates**: a closure whose `date` is before today in Buenos Aires is rejected (`400`).
3. **Partially past range**: a range for today whose `start_time` is earlier than the current
   Buenos Aires time is rejected (`400`). A range starting at the current minute is accepted, and
   a whole-day closure for today is accepted.
4. **Overlap** (R2): a reservation or candidate slot is affected when
   `block.starts_at < closure_end AND block.ends_at > closure_start`. A whole-day closure is the
   interval `[00:00, next day 00:00)`, so every block that touches that date is affected.
5. **Availability** (`GET /api/restaurants/{id}/availability`):
   - a whole-day closure for the requested date makes the day `open: false` with no slots;
   - a range marks every candidate slot whose 90-minute block overlaps it as `available: false`;
   - a date with no closures behaves exactly as before.
6. **Tables for a start** (`GET /api/restaurants/{id}/availability/tables`): a start inside a
   closure is rejected with `400` (the slot is not offered; a hand-edited URL is invalid input).
7. **Confirmation** (`POST /api/reservations`): after revalidating the shift and before choosing a
   table, a start whose block overlaps a closure raises a `409`
   ("Ese horario ya no está disponible. Elegí otro."). This closes the race between the diner's
   review and the restaurant's closure.
8. **Affected reservations**: when a closure is applied, the affected set is the restaurant's
   reservations with `status = 'confirmed'` whose block overlaps the closure range (rule 4).
   Reservations of other restaurants are never touched.
9. **Warning before applying** (R3): if the affected set is not empty and the request is not
   confirmed, nothing is written and the API answers `409` with each reservation's id, date,
   start time, end time and party size. The page sends the same payload with `confirmed: true` and
   `acknowledged_reservation_ids`. If that set differs from the current affected set, the API
   answers `409` again with the updated list; only an exact match applies the closure.
10. **Applying a closure** (one transaction): insert the `Closure`; for every affected reservation
    set `status = 'cancelled'` and `cancelled_at = now` (UTC); delete its `Cart` (and its items by
    cascade). The associated `Order` is not modified: the existing restaurant views treat the
    order of a cancelled reservation as cancelled (spec 008 US-18 S3; spec 009 P12). The table is
    freed because availability counts only `confirmed` reservations.
11. **Idempotency**: a request whose `request_id` already belongs to a closure of the same
    restaurant returns that closure (`200`) without touching any reservation again. A request id
    that belongs to another restaurant hits the unique constraint and answers `409` without
    revealing the other closure.
12. **Mail** (FR-007, assumption): after the commit, one mail per affected diner with the
    restaurant name, the date and the reservation time. A `MailError` is logged and does not undo
    the closure.
13. **Listing**: `GET /api/restaurante/bloqueos` returns the authenticated restaurant's closures
    with `date >= today` in Buenos Aires, ordered by date and start time (whole-day closures sort
    before ranges of the same day). Each item includes `id`, `date`, `start_time`, `end_time`,
    `all_day` and `created_at`.
14. **Deleting**: `DELETE /api/restaurante/bloqueos/{id}` removes the closure only if it belongs to
    the authenticated restaurant (`404` otherwise). It does not restore cancelled reservations
    (FR-009); availability is recomputed from the remaining closures.
15. **Isolation**: every query filters by the authenticated `restaurant_id` (FR-010).
16. **Now**: `now` is passed into the service with the current Buenos Aires time as default, so
    tests fix it (the repository fixture sets Monday 2 November 2026, 09:00).

## Invariants and their tests

- A closure always has either both times or neither: `test_us32_s6_rejects_invalid_ranges_and_past_dates`.
- A range never ends before or at its start: the database `end_after_start` check plus the same test.
- A double confirmation applies once: unique `request_id`
  (`test_us32_edge_repeated_request_applies_once`).
- A closure never cancels a reservation of another restaurant:
  `test_us32_edge_restaurant_only_sees_and_removes_its_closures`.
- Cancelling a reservation frees its table and its order counts as cancelled:
  `test_us32_edge_cancelled_reservation_releases_table_and_order`.
- A blocked start cannot be confirmed: `test_us32_edge_blocked_start_cannot_be_confirmed`.

## What is deliberately not stored

- No recurrence rule ("todos los lunes"): out of scope.
- No refund or payment state: US-38/US-56.
- No `Order.status = 'cancelled'`: derived from the reservation (spec 009 P12).
- No diner notification record: the mail is best effort, like the verification mail.
