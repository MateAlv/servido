# Closures API Contract (US-32)

Base path: `/api`. All endpoints require a valid restaurant session. A missing or expired session
answers `401`; a diner token answers `403`. Every query is scoped to the authenticated restaurant.
A closure that belongs to another restaurant is indistinguishable from a missing one (`404`).

## `POST /restaurante/bloqueos`

Creates a closure for a whole day or a time range. If the range contains confirmed reservations,
the first request answers `409` with the affected list and writes nothing. The page then repeats
the same payload with `confirmed: true` and the acknowledged ids.

### Request

```json
{
  "date": "2026-11-10",
  "start_time": "18:00",
  "end_time": "21:00",
  "request_id": "4c1f5a3e-9d2b-4f7a-8c11-0e6b2a9d4f31",
  "confirmed": false,
  "acknowledged_reservation_ids": []
}
```

| Field | Rules |
| --- | --- |
| `date` | Buenos Aires local date; today or later |
| `start_time`, `end_time` | Both `null` for a whole-day closure; otherwise both present with `end_time > start_time` |
| `request_id` | UUID generated by the page once per block attempt; unique |
| `confirmed` | `false` for the first request; `true` only after the restaurant saw the affected list |
| `acknowledged_reservation_ids` | The ids shown in the warning; compared with the current affected set when `confirmed` is `true` |

### Response `201 Created`

```json
{
  "id": "a41e7b20-5c3d-4a9e-b2f1-7d8c0e4a6b15",
  "date": "2026-11-10",
  "start_time": "18:00",
  "end_time": "21:00",
  "all_day": false,
  "created_at": "2026-11-08T12:00:00-03:00"
}
```

A whole-day closure returns `"start_time": null`, `"end_time": null`, `"all_day": true`.

A repeated request with the same `request_id` returns `200 OK` with the existing closure and does
not cancel anything again.

### Warning `409 Conflict`

Returned when the range has confirmed reservations and the request is not confirmed, or when the
acknowledged set differs from the current affected set (a reservation was created or cancelled
between the warning and the confirmation). Nothing is written.

```json
{
  "detail": {
    "message": "Hay reservas confirmadas en ese horario.",
    "reservations": [
      {
        "reservation_id": "b73c1f44-2a8e-4d6f-9c0a-1e5d7b3f8a22",
        "date": "2026-11-10",
        "start_time": "20:00",
        "end_time": "21:30",
        "party_size": 3
      }
    ]
  }
}
```

`message` and every reservation are shown in Spanish. No diner identity or contact data is
returned.

### Other errors

| Status | When | Message (Spanish) |
| --- | --- | --- |
| `400` | `date` before today | `No podés bloquear una fecha pasada.` |
| `400` | only one of the two times | `Elegí la hora de inicio y la de fin, o bloqueá el día completo.` |
| `400` | `end_time <= start_time` | `La hora de fin debe ser posterior a la de inicio.` |
| `400` | today's range already started | `Esa franja ya comenzó. Elegí una hora posterior o bloqueá el día completo.` |
| `409` | `request_id` already used by another restaurant | `No pudimos guardar el bloqueo. Volvé a intentarlo.` |

### Side effects when applied

In one transaction:

1. The `Closure` row is inserted.
2. Every affected reservation changes to `status = "cancelled"` and gets `cancelled_at` (UTC).
3. Its `Cart` is deleted. Its `Order` is not modified: the existing restaurant views treat the
   order of a cancelled reservation as cancelled (spec 008 US-18 S3; spec 009 P12).
4. Its table is free again because availability counts only `confirmed` reservations.

After the commit, one mail is sent to each affected diner with the restaurant name, the date and
the reservation time. A mail failure is logged and does not undo the closure.

## `GET /restaurante/bloqueos`

Returns the authenticated restaurant's current closures: `date >= today` in Buenos Aires, ordered
by date and start time.

### Response `200 OK`

```json
{
  "closures": [
    {
      "id": "a41e7b20-5c3d-4a9e-b2f1-7d8c0e4a6b15",
      "date": "2026-11-10",
      "start_time": "18:00",
      "end_time": "21:00",
      "all_day": false,
      "created_at": "2026-11-08T12:00:00-03:00"
    },
    {
      "id": "c92d4e11-8f7a-4b3c-a6d5-2e9f1c0b7a44",
      "date": "2026-11-12",
      "start_time": null,
      "end_time": null,
      "all_day": true,
      "created_at": "2026-11-08T12:05:00-03:00"
    }
  ]
}
```

An empty result returns `200` with `"closures": []`.

## `DELETE /restaurante/bloqueos/{closure_id}`

Removes one closure of the authenticated restaurant.

### Response `204 No Content`

No body. A closure from another restaurant or an unknown id returns `404`.

Deleting a closure does not restore the reservations it cancelled (FR-009). Availability is
recomputed from the remaining closures, so the shifts are offered again unless another closure
still covers the date or time.

## Availability integration (existing endpoints, no contract change)

`GET /restaurants/{restaurant_id}/availability` and
`GET /restaurants/{restaurant_id}/availability/tables` keep their current response shape.

- A whole-day closure for the requested date answers `open: false` with no slots.
- A time range marks every slot whose 90-minute block overlaps it as `available: false`; the
  other slots keep their usual availability.
- `availability/tables` rejects a start inside a closure with `400`
  (`Ese horario está bloqueado.`), because the slot is not offered.
- `POST /reservations` answers `409`
  (`Ese horario ya no está disponible. Elegí otro.`) when the start became blocked between the
  review and the confirmation.

## Restaurant cancellation view

No change to `GET /restaurante/cancelaciones`: the reservations cancelled by a closure appear
there with `status: "cancelled"`, their `cancelled_at`, and
`preordered_order: { "status": "cancelled" }` when they had an order (US-18 S3).
