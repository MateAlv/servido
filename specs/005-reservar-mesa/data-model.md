# Data model: reservar mesa (US-11, US-13)

Two groups of tables:

- **Owned by spec 004** (US-8, US-10): the opening shifts (`turnos`) and the table groups (`table_inventory`). This feature reads them; the only change it asks of 004 is the `seating_area` of each group (team decision of 28/10, below).
- **Owned by this feature**: `reservations`. US-11 only reads it to compute availability; US-13 writes it when the diner confirms.

Decisions of 28/10 (team, pending PO) that shape this model: D1 how a reservation identifies its table, D2 what "la mesa asignada" is, D3 the seating area of each group, D5 90-minute reservations every 30 minutes, D6 a fixed catalog of seating areas, D7 a reservation is confirmed on creation, D8 overlapping reservations of one diner are warned about, not blocked, D9 a restaurant cannot remove or change a booked table group. Rationale in [research.md](research.md).

## Provided by spec 004 (consumed here)

### Table groups (`table_inventory`) — spec 004, US-10

One row is a group of equivalent tables: `quantity` tables of `capacity` seats in one `seating_area`.

| Column | Type | Null | Constraints / behavior |
| --- | --- | --- | --- |
| `id` | UUID | no | Primary key. **Not stable**: `PUT /api/restaurante/mesas` deletes and recreates every group, so nothing may reference it |
| `restaurant_id` | UUID | no | FK → `restaurantes.id_restaurante` |
| `capacity` | `INTEGER` | no | `> 0` |
| `quantity` | `INTEGER` | no | `> 0` |
| `seating_area` | `VARCHAR(20)` | no | **New (D3, D6)**: `CHECK (seating_area IN ('indoor', 'outdoor', 'terrace'))`. The migration sets `indoor` on existing rows |
| `available` | `BOOLEAN` | no | Default `TRUE`; `FALSE` removes the group from availability (US-10 S2) |

The group's stable identity is **(restaurant, capacity, seating area)**: the unique constraint changes from `(restaurant_id, capacity)` to `(restaurant_id, capacity, seating_area)`.

### Shift (`turnos`) — spec 004, US-8

`restaurant_id`, `day_of_week` (ISO 1 = Monday … 7 = Sunday), `start_time`, `end_time`, `active`. Shifts do not cross midnight (004 rejects `end_time <= start_time`).

## Owned by this feature

### `reservations` (Reserva)

Model: `backend/app/models/reservation.py`. Created by one migration after `005_merge_feature_heads`, together with the `seating_area` column of 004.

| Column | Type | Null | Constraints / behavior |
| --- | --- | --- | --- |
| `id` | UUID | no | Primary key |
| `diner_id` | UUID | no | FK → `comensales.id_comensal`, `ON DELETE RESTRICT` |
| `restaurant_id` | UUID | no | FK → `restaurantes.id_restaurante`, `ON DELETE RESTRICT` |
| `table_capacity` | `INTEGER` | no | Capacity of the assigned group; `CHECK (table_capacity > 0)` |
| `seating_area` | `VARCHAR(20)` | no | Seating area of the assigned group; same `CHECK` as `table_inventory` |
| `table_number` | `INTEGER` | no | Which table of the group, from 1 to the group's `quantity` when booked. **Internal**: never shown (spec 004, FR-005); `CHECK (table_number > 0)` |
| `party_size` | `INTEGER` | no | `CHECK (party_size > 0 AND party_size <= table_capacity)` |
| `starts_at` | `TIMESTAMPTZ` | no | Start of the block, UTC |
| `ends_at` | `TIMESTAMPTZ` | no | Set by the service; `CHECK (ends_at - starts_at = INTERVAL '90 minutes')` (D5). Not a generated column: `timestamptz + interval` is not immutable, and PostgreSQL only accepts immutable expressions there, while the difference of two `timestamptz` is |
| `status` | `VARCHAR(20)` | no | `confirmed` or `cancelled`, `CHECK`, default `confirmed` (D7). Only `confirmed` exists until cancellations (Sprint 3) |
| `request_id` | UUID | no | Generated by the page once per review and sent with the confirmation; **unique**. A repeated confirmation (double click, retry after a lost response) finds the existing reservation instead of creating another |
| `created_at` | `TIMESTAMPTZ` | no | Default `CURRENT_TIMESTAMP` |

Constraints and indexes:

- `ex_reservations_table_no_overlap` (D1, risk 2, SC-003): `EXCLUDE USING gist (restaurant_id WITH =, table_capacity WITH =, seating_area WITH =, table_number WITH =, tstzrange(starts_at, ends_at) WITH &&) WHERE (status = 'confirmed')`. Two confirmed reservations can never hold the same table of a group at overlapping times; a cancelled one frees it. Needs `CREATE EXTENSION IF NOT EXISTS btree_gist` (bundled with PostgreSQL; `downgrade()` leaves it).
- `uq_reservations_request_id` (double submit): unique on `request_id`. A diner **may** hold two reservations at the same restaurant and start (two tables for a big group, D8 warns about it), so the duplicate check is per confirmation request, not per restaurant and start.
- All of the above are declared in the model (`__table_args__`: `ExcludeConstraint`, `Index`, `CheckConstraint`), so `alembic check` in CI sees no drift between the model and the migration.
- `ix_reservations_restaurant_id_starts_at` for the availability queries, and `ix_reservations_diner_id_starts_at` for the overlap warning.

Not added yet: order links, deposit, payment, arrival or prep times (later specs).

## Rules (single source: `backend/app/services/availability.py`)

1. **Window**: the requested BA date becomes `[date 00:00, date+1 00:00)` in `America/Argentina/Buenos_Aires`, compared in UTC.
2. **Open**: the weekday is open if it has an active shift; otherwise `open = false` and no slots.
3. **Candidate starts** (D5): every 30 minutes from each shift's start while `start + 90 minutes <= end`. Starts already past (today) are dropped.
4. **Maximum party size**: `max(capacity)` over the restaurant's `available` groups, `0` without any.
5. **Free tables of a group at a block**: `quantity` minus the number of **distinct** `table_number`s of that group (same capacity and seating area) held by confirmed reservations that overlap the block (`starts_at < block_end AND ends_at > block_start`). Counting reservations instead would be wrong: table 1 can hold a 19:00 and a 21:00 reservation, and both overlap a 20:00 request, but they use one table, not two.
6. **Slot available**: at least one `available` group with `capacity >= party_size` has a free table.
7. **Table groups for a start** (`/availability/tables`): every `available` group with `capacity >= party_size` and at least one free table, with its free count, ordered by `capacity` then `seating_area`.
8. **Assigned table** (D2, FR-014): the group with the smallest `capacity` among those of rule 7, filtered by the chosen seating area; with "Sin preferencia", ties go `indoor`, `outdoor`, `terrace`. The page computes it from rule 7's list to show it in the review, and sends it in the confirmation.
9. **Confirmation** (US-13, inside one transaction):
   1. If a reservation with this `request_id` already exists for this diner, return it (`200`): it was a repeated submit.
   2. Validate the shape: start on the 30-minute grid, `party_size >= 1` (`400` otherwise).
   3. Lock the chosen group `FOR UPDATE`. That serializes two confirmations on one group (no false `409` while another table is free) and a concurrent `PUT /api/restaurante/mesas`. If the group is gone after the lock (the restaurant re-saved its tables meanwhile), look it up again by (restaurant, capacity, seating area) once; if it doesn't exist, isn't `available` or is smaller than `party_size`, answer `409`.
   4. Revalidate everything that can change while the diner reviews, each as `409` with its own message: the start is now past, its 90 minutes are no longer inside a shift, `party_size` exceeds the current `max_party_size`, the restaurant stopped being bookable.
   5. Pick the lowest `table_number` in `1..quantity` with no overlapping confirmed reservation of that group (rule 5's query). None free → `409`.
   6. Insert with `status = 'confirmed'`. The exclusion constraint is the last guard: if it fails anyway, `409`.
10. **Overlap warning** (D8, US-13 S6): the review lists the diner's confirmed reservations of that day and flags any that overlaps the chosen block. It never blocks the confirmation, also at the same restaurant and start.
11. **Inventory changes** (replaces the conflict-check stub of spec 004; decision D9, pending PO): when `PUT /api/restaurante/mesas` lowers a group's `quantity` to `Q`, it conflicts if a confirmed reservation of that group that hasn't ended (`ends_at > now`) has `table_number > Q`. Removing the group, marking it unavailable, or changing its capacity or seating area means `Q = 0` for the old group. The conflict lists those reservations (date, time, party size), answers `409` and changes nothing; the restaurant screen shows the list. The check runs inside the inventory transaction, after the groups are locked, with the same session: its interface becomes `check_reservation_conflict(session, restaurant_id, capacity, seating_area, new_quantity)`.
12. **Now**: `now` is passed into the service (a parameter with the current time as default), so tests fix it; "today" and "past" are evaluated in `America/Argentina/Buenos_Aires`, never with `date.today()` on the server's UTC clock.
13. **Bookable**: the map lists only bookable restaurants (coordinates, an active shift, an available group), and only those can be confirmed. The availability reads answer `404` only for an unknown restaurant id; a known restaurant without shifts or tables answers `200` with `open: false` or `max_party_size: 0`, so the page can say it has no tables yet (US-11 edge case). At confirmation, a restaurant that stopped being bookable during the review answers `409` (rule 9.4).

## Invariants and their tests

- No two confirmed reservations on one table of a group at overlapping times: the exclusion constraint (`test_us13_edge_database_rejects_a_double_booking`).
- One confirmation request cannot create two reservations: the unique `request_id` (`test_us13_edge_repeated_request_returns_the_same_reservation`); two different requests at the same restaurant and start create two (`test_us13_s6_overlapping_reservation_can_still_be_confirmed`).
- Free tables are counted by table, not by reservation (`test_us11_edge_one_table_with_two_reservations_counts_once`).
- No reservation outside the shifts, in the past or for a party above the maximum: the service, `409` when it became impossible during the review, `400` for a malformed request (`test_us13_edge_rejects_…`).
- A restaurant cannot leave a future reservation without a table: the inventory check (`test_us13_edge_inventory_change_keeps_booked_tables`).

## Where the selection lives

Until the diner confirms, the selection lives in the URL of `/reservar/:restauranteId` (`?fecha=&hora=&personas=&tipo=`): nothing is stored on the server, and going back from the review keeps every value (US-13 S3). The confirmation request carries it whole, plus the group shown in the review.

## Real and test restaurants (D4)

Only restaurants stored in the database can be booked. A restaurant is **bookable** when it has coordinates, at least one active shift and at least one available table group. The map and the detail show bookable restaurants next to the test restaurants of spec 002 (`frontend/src/data/restaurants.fixture.ts`), which keep their «Próximamente» booking card. The reservation fixture (`reservationAvailability.fixture.ts`) is deleted when the availability endpoints are wired.
