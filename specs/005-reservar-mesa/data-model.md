# Data model: reservar mesa (US-11)

Two groups of tables:

- **Owned by spec 004** (US-8, US-10): `tables` and the opening hours. This feature reads them and must not create or modify them.
- **Owned by this feature**: `reservations`. US-11 never writes a row; it only reads them to compute availability.

A temporary frontend mock mirrors the API while spec 004 is missing; it is described at the end of this file and is not part of the data model.

## Provided by spec 004 (consumed here)

### `tables` (Mesa) — spec 004, US-10

| Column | Type | Null | Constraints / behavior |
| --- | --- | --- | --- |
| `id` | UUID | no | Primary key |
| `restaurant_id` | UUID | no | FK → `restaurantes.id_restaurante`, `ON DELETE CASCADE` |
| `label` | `VARCHAR(40)` | no | Name the diner sees, e.g. `Mesa 4` |
| `capacity` | `INTEGER` | no | `> 0` (FR-004 of spec 004) |
| `seating_area` | `VARCHAR(20)` | no | `CHECK (seating_area IN ('indoor', 'outdoor', 'terrace'))` |
| `active` | `BOOLEAN` | no | Default `TRUE`; `FALSE` removes it from availability (US-10 S2) |

**Open point**: the spec of 004 describes groups of tables (capacity × count). This feature needs one row per physical table so that the assignment and US-13's review name a single table (US-13 S2, "la mesa asignada"). The restaurant screen can still ask for groups and create N rows in one action. Pending with the PO; recorded in `plan.md` and `specs/README.md`.

### Shift (`Turno`) — spec 004, US-8

`restaurant_id`, `weekday` (ISO 1 = Monday … 7 = Sunday), `start_time`, `end_time`, `active`. Shifts do not cross midnight: 004 rejects `end_time <= start_time` (US-8 S2), so US-11 assumes every shift ends the same day.

## Owned by this feature

### `reservations` (Reserva)

Model: `backend/app/models/reservation.py`, table `reservations` (English per the `AGENTS.md` glossary).

| Column | Type | Null | Constraints / behavior |
| --- | --- | --- | --- |
| `id` | UUID | no | Primary key, generated by the application |
| `diner_id` | UUID | no | FK → `comensales.id_comensal`, `ON DELETE RESTRICT` |
| `restaurant_id` | UUID | no | FK → `restaurantes.id_restaurante`, `ON DELETE RESTRICT` |
| `table_id` | UUID | no | FK → `tables.id`, `ON DELETE RESTRICT` |
| `starts_at` | `TIMESTAMP WITH TIME ZONE` | no | Start of the 90-minute block, stored in UTC |
| `ends_at` | `TIMESTAMP WITH TIME ZONE` | no | Generated column: `starts_at + INTERVAL '90 minutes'` |
| `party_size` | `INTEGER` | no | `CHECK (party_size > 0)`; the upper bound is the restaurant's maximum (below), validated by the API and the write path, not by a column |
| `created_at` | `TIMESTAMP WITH TIME ZONE` | no | Default `CURRENT_TIMESTAMP` (UTC) |

Constraints:

- `ck_reservations_party_size_positive`: `party_size > 0`.
- `ex_reservations_table_no_overlap`: `EXCLUDE USING gist (table_id WITH =, tstzrange(starts_at, ends_at) WITH &&)`. Requires `CREATE EXTENSION IF NOT EXISTS btree_gist` in the migration (`downgrade()` drops the constraint but leaves the extension, which is harmless and may be used by later features).
- Index `ix_reservations_restaurant_id_starts_at` for the per-restaurant availability query.
- Consistency check `starts_at = date_trunc('minute', starts_at)`? **No**: the 30-minute grid is a rule of the service, not of the data. Enforcing it in the database would reject future manual/administrative reservations without a product reason.

Not added yet:

- `status` (`confirmed` / `cancelled`): arrives with US-13, the only story that creates or cancels reservations. Adding it now would be a column with a single possible value.
- `prep_start_time`, order links, deposit, payment: later specs (US-17, US-41, US-54).

## Availability rules (single source: `app/services/availability.py`)

1. Convert the requested BA date to a UTC window: `[date 00:00 BA, date+1 00:00 BA)` using `ZoneInfo("America/Argentina/Buenos_Aires")`.
2. If the weekday has no active shift, `open = false` and `slots = []`.
3. Candidate starts: every 30 minutes from `shift.start_time` while `start + 90 minutes <= shift.end_time`.
4. Drop candidates that are already in the past (today only).
5. The restaurant's **maximum party size** is `max(t.capacity)` over its `active` tables (`0` if it has none). Each reservation holds one table, so a group bigger than the largest table has nowhere to sit; it is never offered.
6. A candidate is `available` if at least one table of the restaurant is `active`, has `capacity >= party_size` and overlaps no reservation: `NOT EXISTS (SELECT 1 FROM reservations r WHERE r.table_id = t.id AND r.starts_at < candidate_end AND r.ends_at > candidate_start)`.
7. Available tables for a chosen start are the tables that satisfy the same predicate, ordered by `seating_area`, then `capacity`, then `label`.
8. A `party_size` above the restaurant's maximum is answered with the cap (`max_party_size`) and no slots/tables: the read endpoint does not create anything and the UI clamps the value, while US-13's write path rejects it with `400`. A `party_size` within the cap that finds no free table with enough capacity, or no table of the chosen seating area, returns an empty list (S7), not an error.
9. A restaurant without active tables has `max_party_size = 0`, `open` as its shifts say and no slots; the page says it has no tables yet.

## Maximum party size (not stored)

The restaurant defines the largest group it accepts through the tables it loaded (spec 004, US-10): `max_party_size = max(capacity)` over the `active` tables, `0` when there is none. It is computed by `app/services/availability.py` and returned by the availability endpoint; there is no `max_party_size` column in `restaurantes`.

Why not a restaurant-level field: the spec assumes one reservation per table, so a bigger group could not be seated, and a second number would duplicate what the tables already encode (two sources of truth for one rule). If the PO later wants a group split across tables, that is a different product rule and a spec change, not a hidden column.

Consequences:

- The diner's input is bounded (`QuantityStepper` `min={1}` and `max={max_party_size}`), and a URL value above the cap is clamped with a notice.
- The read endpoints never offer a slot or a table for a party above the cap; they report the cap so the UI can explain it.
- US-13's `POST` rejects `party_size > max_party_size` with `400` (not in this feature).

## Invariants and tests

- No two reservations may overlap on the same table (SC-003, risk 2): the exclusion constraint, tested by `test_us11_edge_database_rejects_overlapping_reservations` (two inserts with a 30-minute shift must raise `IntegrityError`).
- A slot is never offered outside the shifts (SC-002): `test_us11_s3_returns_only_slots_inside_shifts`.
- No group larger than the restaurant's biggest active table is offered (FR-013): `test_us11_edge_returns_the_restaurant_max_party_size`, `test_us11_edge_returns_no_max_without_active_tables` and `test_us11_edge_offers_no_slots_above_the_restaurant_maximum`.
- Reservations never point to a table of another restaurant: the endpoints derive both from the same `restaurant_id`; US-13 will add the same check in the write path.

## Where the selection lives (no draft row)

There is no draft reservation. Until US-13 confirms, the selection (date, time, party size, seating preference) lives in the URL of `/reservar/:restauranteId` — `?fecha=&hora=&personas=&tipo=` — and reaches the server only in the confirmation request, which carries it whole. Which table is used is not part of the selection (team decision of 23/10, following `prototipo-us11.html`): the page reports whether a table is free for the chosen preference and the table is assigned at confirmation. Consequences:

- Reloading, going back or reopening the link keeps the selection without any server state.
- Nothing is written to the database, to `sessionStorage` or to a cookie.
- The seating preference is not stored in the reservation: the assigned table already has its `seating_area`.
- A `personas` in the URL above the restaurant's maximum is clamped to `max_party_size` with a notice once the response gives the cap; a non-numeric or smaller-than-1 value falls back to 1.
- A `hora` in the URL that is not an available slot is cleared with a notice, so a stale or hand-edited link cannot keep an occupied time.

## Mock data (frontend only)

While spec 004 is missing, or while the endpoints are not wired, the screen reads `frontend/src/data/reservationAvailability.fixture.ts` through `frontend/src/api/availability.ts`. It is **not** part of this data model:

- It never reaches the database and no backend code imports it.
- It mirrors the two responses of `contracts/availability-api.md`: `open`, `duration_minutes`, `max_party_size`, `slots` and `tables` with the same field names, so swapping it for the typed client changes one file.
- Values: Monday closed; shifts 12:00–15:00 and 20:00–23:30 on the other days; five tables where `Mesa 5` is `active: false` and never appears, and the four offered are `Mesa 1` and `Mesa 2` indoor for 2, `Mesa 3` outdoor for 4, `Mesa 4` terrace for 4; therefore `max_party_size: 4`. The 20:30 slot is `available: false` (an occupied slot, which US-13 would otherwise have to create). At 21:00 `Mesa 4` is taken, so a party of 4 that prefers Terraza gets the S7 empty state while the slot stays available for the other areas. Past times removed; only tables with `capacity >= party_size`.
- The page caps the stepper at `max_party_size` and clamps a URL value above it, so the mock never receives a party the restaurant cannot seat; it has no HTTP layer to answer `400`.
- It is labelled «Datos de prueba» in the UI and its removal is `T018` in `tasks.md`.
- The real data always wins: when the endpoints answer, the page stops using the fixture in the same PR.
