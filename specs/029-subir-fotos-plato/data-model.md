# Data model — Review photos

## Review

Reuse `reviews.id`, the unique `reservation_id` constraint, rating, optional comment and spend, and publication timestamp. The reservation supplies diner and restaurant ownership. A review has zero to four ordered photos. Existing reviews have zero photos and require no backfill.

## ReviewPhoto

| Field | Type | Constraint |
| --- | --- | --- |
| `id` | UUID | Primary key, generated by the server, also used as the opaque media identifier |
| `review_id` | UUID | Non-null foreign key to `reviews.id`, indexed via the unique position constraint |
| `position` | Small integer | Required, 1 through 4, unique with `review_id` |
| `media_type` | String | Required, JPEG, PNG or WebP from server validation |
| `created_at` | Timezone-aware timestamp | Required, stored in UTC |

Derive the storage filename from the photo UUID and validated type. Derive the API URL from the UUID. Never persist the user's original path or filename as a storage key. The range and uniqueness constraints enforce the maximum of four rows per review.

## Lifecycle and visibility

- Selections and preview URLs live in the form draft before publication. They have no durable server identity at that point.
- Validate the entire submission. Save photo files and metadata with the existing review publication transaction as the visibility boundary. A file is deliverable only when its committed photo row exists.
- On known rollback, clean up files written by that request. On an uncertain commit, establish whether metadata exists before deleting. Repeated publication retains the existing 409 and does not attach files to the first review.
- A newer visit changes the public selection without moving, deleting or duplicating photo data. The restaurant can still load photos and existing replies for its older reviews.
